# 资质查询与预览体验优化方案

> 日期：2026-08-06  
> 范围：资质查询结果出现慢、标准 PDF 预览体验不佳、部分华为手机无法打开内嵌预览。

## 一、当前代码结论

### 1. 资质查询为什么显得慢

当前资质查询有两条主要链路：

| 场景 | 前端入口 | 后端服务 | 当前特点 |
|------|----------|----------|----------|
| 按机构 / 标准 / 项目搜资质明细 | `public/js/app-qual-search.js` 的 `doQualSearch()` | `QualificationService.searchQualifications()` | CNAS 与 CMA 分开查，返回完整结果后一次性渲染 |
| 按标准聚合查询 | `public/js/app-qual-search.js` 的 `doQualByStdSearch()` | `QualificationService.searchByStandard()` | 先按标准分组统计，再批量取每组明细 |
| 搜索结果资质徽章 | `fetchQualBadges()` | `queryByStdCodes()` | 使用 `std_code_norm IN (...)`，属于较快路径 |

核心慢点不是单一 Bug，而是“查询策略 + 呈现策略”叠加：

1. `searchQualifications()` 为了支持标准号、标准名称、机构名、检测项目、类别等多字段搜索，使用大量 `OR + LIKE '%关键词%'`。
2. SQLite 在这种条件下很难真正利用 `std_code_norm` / `std_code_base` 索引，容易变成扫描资质表后再排序。
3. 默认同时查 CNAS 与 CMA，两张表分别执行一次重查询。
4. 前端先显示一个 spinner，必须等完整接口返回后才渲染；即使后端只慢几百毫秒，用户体感也是“没反应”。
5. “按标准查”还需要 `GROUP BY`、`COUNT(DISTINCT ...)` 和第二轮明细查询，数据量变大后会更明显。

### 2. 预览为什么体验不够好

当前预览链路：

| 场景 | 当前行为 | 体验问题 |
|------|----------|----------|
| 本地库命中 | `/api/preview/request` 返回 `ready`，前端加载 PDF | 首次动态加载 PDF.js / pdfh5 资源，仍会有等待 |
| 本地库未命中 | 后端自动下载并入库，前端轮询任务 | 只显示“正在自动下载”和轮询次数，用户不知道卡在哪个源 |
| 桌面 Web | overlay 内自研 PDFViewer canvas 渲染 | 缺少浏览器原生搜索、打印、下载、手势兼容 |
| 手机端 | pdfh5 内嵌预览 | 部分华为浏览器 / WebView 可能打不开或资源加载失败 |
| Electron | 已偏向系统浏览器打开 | Web 和手机端还缺少明显的“原生打开”兜底入口 |

因此预览优化应同时解决两类问题：

1. **打开前反馈**：告诉用户“正在查本地库 / 搜索哪个源 / 下载中 / 入库中 / 渲染中”。
2. **打开方式兜底**：内嵌预览失败或兼容性差时，提供醒目的“用浏览器原生打开 / 复制链接 / 下载后打开”。

## 二、优化目标

### 目标 A：资质查询先快后全

标准号类查询优先走索引快路径，尽快展示可信结果；全文模糊搜索作为补充，不阻塞首屏。

验收标准：

- 输入 `GB/T 3324-2017`、`3324`、`GB/T 3324` 等标准号形态时，首批结果明显更快出现。
- 页面不再长时间只显示一个 spinner。
- 精确命中、同系列/跨年命中、全文匹配在 UI 上有清晰区分。
- 查询结果仍保留 CNAS/CMA 来源筛选和数量限制。

### 目标 B：预览有清晰任务反馈

预览不只是“等”，而是让用户知道系统正在做什么。

验收标准：

- 本地库命中时显示“本地文件，正在打开”。
- 未命中自动下载时显示当前阶段、当前来源、耗时、重试提示。
- 下载成功后明确显示“已入库，正在打开预览”。
- 失败时提供“重试”“下载”“用浏览器原生打开 / 复制链接”等可执行动作。

### 目标 C：手机端预览提供原生打开兜底

针对华为手机等内嵌 PDF 兼容不稳定场景，提供不依赖 pdfh5 的打开方式。

验收标准：

- 手机端预览弹层顶部或失败页提供“用浏览器原生打开”。
- pdfh5 加载失败时自动展示兜底按钮，不让用户停在空白页。
- 若系统浏览器仍打不开，用户可一键下载 PDF 后用本机 PDF 应用打开。

## 三、实施方案

### 阶段 1：资质查询快路径

#### 1.1 新增查询类型判断

前端或后端统一判断用户输入类型：

| 输入类型 | 示例 | 处理方式 |
|----------|------|----------|
| 完整标准号 | `GB/T 3324-2017` | 严格查 `std_code_norm = ?` |
| 标准号不带年份 | `GB/T 3324`、`3324` | 查 `std_code_base = ?`，必要时补 `LIKE` |
| 普通关键词 | `木家具`、机构名、检测项目 | 走全文模糊查询 |

优先建议在后端做，保证 API 调用方都受益。

#### 1.2 拆分“快结果”和“补充结果”

新增或改造接口返回结构：

```json
{
  "mode": "standard_code",
  "quickItems": [],
  "fuzzyItems": [],
  "hasMore": false
}
```

前端先渲染 `quickItems`，再显示“正在补充全文匹配…”。

#### 1.3 SQL 优化方向

- 标准号类输入优先使用：
  - `std_code_norm = ?`
  - `std_code_base = ?`
  - `std_code_norm IN (...)`
- 只有普通关键词才走多字段 `LIKE`。
- 避免在快路径里混入 `OR q.std_name LIKE ? OR l.lab_name LIKE ?` 这类扫表条件。
- “按标准查”先只返回分组摘要，用户展开某个标准时再取该组明细，避免一次返回大量嵌套数据。

### 阶段 2：资质查询前端体验

#### 2.1 查询状态细分

把单一 spinner 改为三段状态：

| 状态 | 文案 |
|------|------|
| 标准号快查 | `正在查标准号索引…` |
| 已出首批结果 | `已显示精确命中，继续补充全文匹配…` |
| 全部完成 | `查询完成，共 N 条` |

#### 2.2 结果分区

建议分为：

1. **精确匹配**：同号同年。
2. **同系列 / 跨年提示**：同标准号不同年份，明确标识，避免误导。
3. **全文匹配**：名称、机构、检测项目命中。

#### 2.3 分页和增量加载

- 明细查询保留默认 50 条，但增加“加载更多”。
- 按标准聚合页改为“先显示标准组，展开再加载机构明细”。

### 阶段 3：预览任务反馈重构

#### 3.1 预览任务状态结构

建议后端任务返回增加统一字段：

```json
{
  "status": "downloading",
  "phase": "searching_source",
  "source": "labr",
  "message": "正在 Labr 搜索标准",
  "elapsedMs": 3500,
  "attempt": 2,
  "fileId": null,
  "url": null,
  "error": null
}
```

#### 3.2 阶段枚举

| 阶段 | 说明 | 前端文案 |
|------|------|----------|
| `checking_library` | 查本地文件库 | `正在查询本地库…` |
| `library_hit` | 本地命中 | `已找到本地文件，正在打开…` |
| `searching_source` | 搜索上游源 | `正在 {source} 搜索标准…` |
| `downloading` | 下载 PDF | `正在从 {source} 下载…` |
| `moving_to_library` | 入库 | `下载完成，正在入库…` |
| `ready` | 可预览 | `已入库，正在打开预览…` |
| `failed` | 失败 | `未能打开预览，可重试或下载后打开` |

#### 3.3 前端展示

预览弹层里增加一个小型任务卡：

- 当前阶段文案。
- 当前来源。
- 已耗时。
- 如果有进度则显示百分比，没有进度则显示阶段流转。
- 提供“取消等待”“继续后台下载”“重试”。

### 阶段 4：原生浏览器打开兜底

#### 4.1 按钮位置

建议在三个位置加入：

1. **预览弹层顶部**：`用浏览器打开`。
2. **手机端加载失败页**：主按钮 `用浏览器原生打开`，次按钮 `下载 PDF`。
3. **预览任务等待中**：当超过 5 秒仍未渲染时，显示 `打开方式不兼容？试试浏览器原生打开`。

#### 4.2 行为策略

| 场景 | 推荐行为 |
|------|----------|
| 本地库已命中 | `window.open('/api/preview/file/:id', '_blank')` |
| 手机端内嵌加载失败 | 直接打开当前 PDF URL |
| 华为 / WebView 兼容问题 | 提示“如仍无法打开，请下载后用系统 PDF 应用查看” |
| 还未下载完成 | 按钮禁用或显示“下载完成后可打开” |

#### 4.3 兼容性细节

- 原生打开链接仍使用 `/api/preview/file/:id`，保留登录态与权限校验。
- 下载按钮使用 `?attachment=1`，强制下载。
- 手机端如果 `window.open` 被拦截，自动复制链接并提示用户粘贴到浏览器。
- 不建议移除 pdfh5；保留内嵌预览作为默认体验，原生打开作为强兜底。

### 阶段 5：预览资源加载优化

#### 5.1 PDF.js / pdfh5 预加载

用户进入搜索结果页后，浏览器空闲时预加载 PDF.js 或 pdfh5 核心资源。

#### 5.2 大文件策略

| 文件大小 / 页数 | 默认策略 |
|-----------------|----------|
| 小文件 | 内嵌预览 |
| 大文件或页数多 | 提示可使用原生浏览器打开 |
| 加载失败 | 自动展示原生打开和下载 |

#### 5.3 渲染体验

- PDFViewer 工具栏改为主题化按钮，减少黑底突兀感。
- 桌面端保留内嵌预览，但强化“新标签打开”。
- 手机端降低误触关闭风险，失败页保留上下文和重试按钮。

## 四、流程表

### 资质查询优化流程

| 顺序 | 步骤 | 修改位置 | 输出结果 | 验收方式 |
|------|------|----------|----------|----------|
| 1 | 判断查询类型 | `qualification-service.ts` 或新增 helper | 区分标准号 / 标准号片段 / 普通关键词 | 单元测试覆盖 `3324`、`GB/T 3324-2017`、`木家具` |
| 2 | 新增标准号快路径 | `searchQualifications()` | 标准号类输入优先走索引查询 | 查看查询计划不再完全依赖扫表 |
| 3 | 拆分快结果与全文结果 | 资质 API + 前端 | 首屏先出精确结果 | 页面不再长时间只有 spinner |
| 4 | 按标准查延迟加载明细 | `searchByStandard()` + 前端展开事件 | 先出标准组，展开再取机构明细 | 大结果查询明显更轻 |
| 5 | 增加分页 / 加载更多 | API 与 `app-qual-search.js` | 避免一次撑爆页面 | 连续加载不重复、不丢数据 |
| 6 | 写入测试与文档 | 测试、TODO、WORKLOG | 固化规则 | 回归测试通过 |

### 预览优化流程

| 顺序 | 步骤 | 修改位置 | 输出结果 | 验收方式 |
|------|------|----------|----------|----------|
| 1 | 扩展预览任务状态 | `preview-task-store.ts`、`preview-routes.ts` | 返回 `phase/source/message/elapsedMs` | 轮询接口可看到阶段变化 |
| 2 | 后端写入阶段进度 | `runAutoDownload()` | 搜索源、下载、入库都有状态 | 手动预览未入库标准可看到阶段 |
| 3 | 前端任务卡展示 | `app-preview.js`、CSS | 替代单一“正在自动下载” | 等待时用户知道卡在哪 |
| 4 | 加原生打开按钮 | `app-preview.js`、预览弹层 HTML/CSS | 手机和桌面都能一键新开 PDF | 华为手机可绕过内嵌预览 |
| 5 | pdfh5 失败兜底 | `app-preview.js` | 加载失败时显示原生打开 / 下载 | 模拟错误 URL 能出现兜底 |
| 6 | 预加载 PDF 资源 | `app-pdf-viewer.js` 或入口脚本 | 首次打开更快 | 首次预览等待降低 |
| 7 | 大文件提示策略 | `preview-routes.ts` + 前端 | 大 PDF 推荐原生打开 | 大文件不再让用户误以为卡死 |
| 8 | 回归测试与手机实测 | 手动 + 自动测试 | 覆盖本地命中、自动下载、失败、华为兜底 | NAS 外网环境可用 |

## 五、推荐实施顺序

1. **先做预览任务反馈阶段化**：让自动下载等待过程可感知，先解决“像卡住”的体感问题。
2. **再做资质查询标准号快路径**：解决最常用查询的速度问题。
3. **再做资质结果分区、延迟加载和分页**：属于结构性优化，改动稍大，适合单独验证。
4. **最后做预览原生打开兜底**：专门解决华为手机 / WebView 内嵌 PDF 不兼容问题；等主预览反馈链路稳定后再加，避免同时改动过多导致排查困难。

## 六、风险与注意事项

- 不要把跨年资质混成严格命中；不同年份必须明确标识。
- 国家 CMA 与 CMA 实验室是不同概念，相关徽章和文案不能混用。
- 原生打开不能绕过 `/api/preview/file/:id` 的权限与本地库边界检查。
- 华为手机兼容问题优先用“兜底打开方式”解决，不建议为了某一类 WebView 大改 PDF 渲染器。
- 预览自动下载仍可能消耗上游配额，尤其 Labr，应保留清晰提示。
